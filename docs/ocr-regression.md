## 2. 记录字段

对每张截图记录四项：

- **识别是否正确**：OCR 文字与原文是否一致（错字、漏字、多字）。
- **位置是否准确**：译文块是否盖在原文上，125%/150% 缩放下是否错位。
- **读起来是否通顺**：译文是否可读、语义是否完整（机器翻译质量）。
- **耗时**：框选结束到译文出现的时间（毫秒）。

## 4. 性能预期（代码层面）

从框选结束到译文盖回原位的链路是：裁剪 → OCR（Windows.Media.Ocr，2× 放大）→
段落合并 → 并发翻译 → 背景色采样 → overlay 渲染。

- 裁剪、合并、采样、渲染均为内存操作，通常 < 50 ms。
- OCR 与翻译是主要耗时项：OCR 通常 < 1 秒；翻译按段落并发（最多 6 个在途），
  单段请求通常 < 1 秒。两者叠加，普通网页文字预计在 1～2 秒内完成。
- 风险点：网络慢或翻译引擎无响应时，单段请求超时（Google 2.5 s / MyMemory 6 s）
  可能拖慢整体；完全本地模式（离线翻译 + Ollama）下冷启动会明显更慢。

## 5. 已知限制与最差一类

按代码实现与 OCR/渲染的固有局限，预计最差的几类（待实测确认）：

1. **扫描件 / 低分辨率**：`Windows.Media.Ocr` 对模糊、倾斜、低分辨率文字识别率低。
   2× 放大只能缓解轻度模糊，无法解决严重倾斜和手写体。
2. **复杂背景（视频字幕、游戏半透明面板）**：背景色采样取边框中位数，对渐变或
   半透明背景判断为「非纯色」，改用半透明底板，擦除痕迹会较明显。
3. **多栏 / 表格 / 公式**：段落合并按栏宽与行高启发式切分，复杂排版可能错并；
   符号占比 > 0.3 判为「不翻译」，表格线、公式可能被误保留或误翻译。
4. **过长译文**：字号最小缩到 9px，仍放不下时文字被截断（气泡展开尚未实现）。

## 6. 下一步改进方向

- 换用本地识别模型：`ocr.rs` 的 `Recognizer` trait 已预留，可接入离线模型改善
  低分辨率与扫描件识别。
- 固定区域连续翻译（视频字幕、游戏对话），作为后续特性。
- 译文放不下时改为「点击展开」的气泡，而不是直接截断。
- 非纯色背景改用更智能的底色估计（按原文行框内底色，而不是边框中位数）。
